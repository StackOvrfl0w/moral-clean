## Verified causes and changes

Production product and blog queries called Supabase `.range()` before checking result counts. An excessive offset could raise `PGRST103` before route-level pagination checks ran. Permissive parsing also accepted malformed page values.

- Strict positive integer and safe offset validation now rejects malformed pages before database/cache access.
- Pages after page one validate against shared catalogue, category, filtered or published-blog counts before touching the result cache or issuing a range. Empty page one remains valid; later empty pages return 404.
- Concurrent deletion between count and range returns 404 without retrying or caching the failed page. Permission/connectivity failures remain errors.
- Listing metadata awaits the same request-memoized query as rendering, allowing an HTTP 404 before streaming. Valid metadata and canonical rules are preserved.
- Shared counts and facets retain 900-second caching and existing `catalog`/`blog` invalidation tags. Anonymous SDK clients and normalized queries are memoized per request; no authenticated session is cached globally.
- Persistent product page entries contain rows and pagination rather than duplicate categories, brands and tags. Free-text searches and unknown filters do not create persistent result entries. Query values over 120 normalized characters or containing control characters return 404.
- Card rows retain only the selected image after the existing nullable primary/sort ordering. Detail galleries and database image selection are unchanged. Product and blog pagination have stable ID tie-breakers.

## Query evidence

Deterministic SDK transport tests verify these cold/warm paths; they are not production billing measurements.

| Request | Verified behavior |
|---|---|
| Malformed page | No database request or result cache access |
| Unfiltered page 999 | One cold shared count HEAD; no facets, range or page entry |
| Category page 999 | Existing category count rejects before product/facet lookup |
| Valid unfiltered page 2, cold | Four facet/count reads plus one row read; count HEAD is shared |
| Filtered later page, cold count | Matching count HEAD before row range; count key excludes page/sort |
| Same valid filtered page, warm | No additional database reads |
| Search count plus rows | Tag expansion occurs once per request; no persistent search result entry |
| Blog later page | Published count cache shared across pages and limits |

Read-only sampling of 12 actual product card rows reduced serialized card-array JSON from 16,121 to 9,128 bytes (43.4%), with identical selected images: [payload evidence](cpu-card-payload-2026-10-12.json). This is neither a whole-page reduction nor a Supabase network-payload or billed CPU measurement.

## Remaining risks and limits

- Count caches inherit the existing 900-second lifetime. External database writes must invalidate the existing tags; otherwise newly valid pages can be rejected until refresh. Concurrent deletions are handled safely.
- Repeated identical free-text searches now read the database again across requests. This deliberately bounds persistent cache cardinality but can increase database work for popular searches. Monitor request mix before expanding the policy.
- Cold filtered/blog later pages require a count HEAD. Network latency and database work are distinct from Fluid Active CPU.
- Cold facets still use four parallel reads. Existing broad tag/brand reads and duplicate category reads across independent caches remain possible; no unsupported RPC/index redesign was attempted.
- Existing product specifications are preserved, including inherited data inconsistencies. This branch does not import the separate unreleased SEO implementation.
- GET checks establish server responses and technical eligibility, not Google indexing, ranking or traffic improvements. No new SEO connector outcomes are claimed.
